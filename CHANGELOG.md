## [Unreleased]

### Added

- **Operator-queue REST surface for charger-submitted CSRs (#189)** — first slice of the deferred SignCertificate signing pipeline (#187). New endpoints under `/api/v1/charge-points/{cp_id}/pending-certificate-signings`: `GET` (list, cursor-paginated, filterable by `status ∈ pending|signed|rejected`), `GET /{id}` (detail with the CSR text), `POST /{id}/approve` (body `{ "signed_chain": "...", "approved_by": "..." }` — marks the row signed, dispatches `CertificateSigned.req` to the charger, returns the charger's reply in `charger_status`), `POST /{id}/reject` (body `{ "reason": "..." }` — marks rejected, no charger interaction). Alembic migration `0011` adds `approved_by` / `rejected_at` / `rejected_reason` columns. Approval transitions `pending → signed` via SQL row-state guard, so concurrent approve calls collapse cleanly to one dispatch + one 404. Operator signs offline against whatever CA they want today; an automated signing service (in-house, AWS PCA, etc.) lands later under #187 and uses the same approve-endpoint shape.
- **OCPP 1.6 Security Whitepaper §4.13 SignCertificate (inbound, handler-only).** The gateway now accepts charger-initiated CSRs: the CSR is persisted into the new `pending_certificate_signings` table, a `cp.csr_submitted` Kafka event is published (best-effort) carrying the CSR + the surrogate row id, and the charger gets `Accepted` (or `Rejected` for an empty / whitespace-only CSR). New proto message `CpCsrSubmitted`, new Setting `kafka_topic_cp_csr_submitted`, new metric `eveys_ocpp_sign_certificate_received_total{outcome=accepted|rejected}`, new Alembic migration `0010`. The actual signing pipeline — which CA mints the cert, who approves, how the signed chain is delivered back via `CertificateSigned.req` — is deferred (#187); chargers that don't get a `CertificateSigned` reply re-submit per spec, and pending rows accumulate for operator review. (#186)
- **OCPP 1.6 Core: `ChangeAvailability` (#180)** — operator-facing way to take a connector (or the whole charger) Operative / Inoperative without dropping the WS. New gRPC RPC + REST wrapper at `POST /api/v1/charge-points/{cp_id}/commands/change-availability`. `connector_id = 0` targets the whole charger; > 0 targets a specific connector. Charger may reply `Scheduled` if a session is in flight; the request is honoured at next idle. Negative `connector_id` and missing/unknown `type` rejected at the boundary as `INVALID_ARGUMENT`/`BAD_REQUEST`.
- **OCPP 1.6 Security Whitepaper §4.7: `ExtendedTriggerMessage` (#182)** — sibling RPC to plain `TriggerMessage` with the wider message-type enum that adds `LogStatusNotification` and `SignChargePointCertificate`. Lets operators on the security-log path and certificate-rotation path proactively prompt the charger without a polling loop. New gRPC RPC + REST wrapper at `POST /api/v1/charge-points/{cp_id}/commands/extended-trigger-message`. Reuses the existing `TriggerMessageStatus` (Accepted/Rejected/NotImplemented). Accepts both Whitepaper additions and the Core 6 (per spec — Extended is a superset, not a sibling).
- **OCPP 1.6 Security Whitepaper §4.8: `GetInstalledCertificateIds` (#184)** — list the CA certificates currently installed on the charger. Read-only audit hook; charger is the source of truth (no DB mirror touched). Response carries the §5.1 `hash_data` Dict per installed cert (`hash_algorithm`, `issuer_name_hash`, `issuer_key_hash`, `serial_number`) so an operator can feed any returned identifier directly into a future `DeleteCertificate` call without re-hashing the PEM. New gRPC RPC + REST wrapper at `POST /api/v1/charge-points/{cp_id}/commands/get-installed-certificate-ids`. Vendor-extension hash algorithms outside SHA-2 surface as `null` rather than getting silently coerced to SHA256.
- **`cp.firmware_status_changed` and `cp.diagnostics_status_changed` webhook events** — the last two planned-but-unshipped events from the integration contract. Both fire from the existing OCPP handlers (`FirmwareStatusNotification`, `DiagnosticsStatusNotification`) immediately after the latest-wins Postgres update, with the same best-effort guard the other emitters use. Envelope shape per `docs/integration/03-webhooks.md`: `{cp_id, status}`. Status values are kept as free-form strings for forward-compat with Phase-5 Security profile additions and vendor extensions. New proto messages `CpFirmwareStatusChanged`, `CpDiagnosticsStatusChanged`; new Settings (Kafka topic + webhook URL/enable for each); both events default to enabled. After this lands, every event in the integration contract is wired end-to-end (only `cp.meter` remains intentionally off-by-default — high volume; Kafka subscription is the right channel). (#169)
- **`cp.online` and `cp.offline` webhook events** — the next two planned-but-unshipped events. `cp.offline` is new; `cp.online` was the dispatcher-and-Settings-but-no-producer ghost event whose webhook URL has existed for months without ever delivering. Both are now driven from the WS server's connection lifecycle: `cp.online` published right after the registry marks the charger online, `cp.offline` published only when the registry's compare-and-delete confirms we still owned the key (so a reconnect-to-different-pod race never produces a spurious offline event). New proto message `CpDisconnected` (`pod_id`, `reason ∈ {clean, error}`); reuses the existing `CpConnected` for online. New Settings: `kafka_topic_cp_connected`, `kafka_topic_cp_disconnected`, `webhook_enable_cp_offline`, `webhook_url_cp_offline`. Both events default to enabled — backends subscribed to `cp.online` for months without receiving anything will start receiving deliveries on this version. (#167)
- **`tx.stopped` webhook event**, the long-deferred third-of-four planned-but-unshipped events. Fired immediately after a successful `StopTransaction` DB commit, alongside the synchronous `/api/eveys/sessions/close` REST call — at-least-once belt-and-braces signal so a backend that timed out on the synchronous call gets a second chance to reconcile. Envelope shape per `docs/integration/03-webhooks.md`: `{transaction_id, id_tag, meter_stop_wh, consumed_wh, stop_reason, charger_reported_at}`. `consumed_wh` is pre-computed from the matching `tx.started` so consumers don't have to join. New proto message `TxStopped`, new Settings (`kafka_topic_tx_stopped`, `webhook_enable_tx_stopped`, `webhook_url_tx_stopped`); enabled by default. Replays don't re-emit. ClickHouse landing table out of scope (no current consumer asks; Postgres `transactions.stopped_*` is authoritative). (#165)

### Changed

- CHANGELOG header now carries a one-line "Latest release" callout above the version sections, linking to both the GitHub Release and the in-file section. Each tag updates the same line. (#146)
- **SLO 4 (transaction durability)** now uses a dedicated `eveys_ocpp_stop_transactions_received_total` counter as its denominator. Previously the SLI summed `stop_transactions_total + handler_errors_total` to approximate "received," which both double-counted failures (the entry-time `_total` inc *and* the error inc) and was misdescribed in the docs. New shape: numerator = persisted (`_total`, now incremented after a successful DB commit only), denominator = received (`_received_total`, incremented at handler entry). Recording rule + SLO doc updated. Dashboards using `eveys_ocpp_stop_transactions_total` won't notice in normal operation (transactions almost always persist); during an incident, the metric will lag the received count, which is exactly the signal SLO 4 is built to surface. (#163)

## [0.1.0] - 2026-05-10

First tagged release. Carries everything previously merged on `main` since repo init; the highlights below are what shipped during this cut's window.

### Added

- **Per-transaction telemetry** on `GET /api/v1/transactions/{transaction_id}`. Response now carries a bounded `telemetry` block with SoC start/last percent and a per-phase voltage/current/power snapshot for `L1`/`L2`/`L3`. ClickHouse-backed; absent phases / `null` SoC fields when the charger never reported that dimension. List endpoints intentionally omit `telemetry` (would be N+1 fan-out per cursor row); use the detail endpoint per id, or `/meter-values?transaction_id=…` for the full curve. Contract: `docs/integration/02-gateway-rest-api.md`. (#134)

### Fixed

- **`MeterValues` enum capture.** The handler dropped every OCPP 1.6 enum dimension on the floor — `measurand`, `phase`, `unit`, `context`, `format`, `location` all landed in storage as `*_UNSPECIFIED` regardless of what the charger sent. Existing `/meter-values` consumers filtering on `?measurand=Voltage` (or any other measurand) silently matched nothing. Now translates the wire form to proto enum values; vendor-extension strings still fall through to `*_UNSPECIFIED` and the raw `value` is preserved. Also applies the OCPP 1.6 §6.21.4 default (absent `measurand` → `Energy.Active.Import.Register`). (#135)
- **Storage ↔ API enum naming.** ClickHouse stores the proto enum name (`MEASURAND_VOLTAGE`, `PHASE_L1`); the REST API now consistently exposes the OCPP 1.6 wire form (`Voltage`, `L1`). Translation happens at the route boundary in both directions: `?measurand=` query params translate wire → proto name on input, response fields translate back on output. `*_UNSPECIFIED` and unmapped vendor-extension strings surface as `null` rather than leak the internal sentinel. Closes the loop on the telemetry feature — `telemetry.phases.{L1,L2,L3}` actually populates against a real charger now. (#136)
