# ADR-0025: Configuration reference is generated, not hand-written

| Status | Date | Authors |
|---|---|---|
| Accepted | 2026-05-05 | Mostafa |

## Context

The service exposes ~46 environment-driven knobs via
`src/eveys_ocpp/settings.py` (Pydantic `BaseSettings`). They span
network bind addresses, Kafka durability/latency, Redis TTLs,
backend HTTP timeouts and retry budgets, OCPP defaults like
`heartbeat_interval_seconds`, and the Authorize cache. Operators
running this service in staging or production need to know:

- **What is the variable called.**
- **What is its default and acceptable range.**
- **What does it actually do.**
- **What breaks (or changes) if I flip it.**
- **Is it sensitive (a secret, a token, a password)?**

Today this information lives in three uncoordinated places:

1. The `Field(...)` `default=` and (sometimes) `description=` on the
   Pydantic field itself.
2. Inline comments above the field.
3. ADRs (`ADR-0019` for Kafka producer hardening, `ADR-0023` for the
   backend integration knobs, `ADR-0017` for idempotency).

Operators have no single page that aggregates these. New fields land
without `description=`. Inline comments and ADRs drift as code
evolves. The result: every operational tuning decision becomes a
search across `git log`, the ADRs, and the source.

## Decision

The configuration reference is **generated from `Settings` itself**.
There is **one** Markdown file the operator reads, and that file is
produced by a script that walks `Settings.model_fields`. The source
of truth is the Pydantic model; the doc is a projection of the model.

Concretely:

1. **Every field on `Settings` carries enough metadata to render its
   row in the doc.** That metadata is:

   ```python
   field_name: T = Field(
       default=...,
       description="One sentence: what does this control.",
       json_schema_extra={
           "category": "kafka_producer",         # required, see categories below
           "impact": "Lowering tightens batching latency at the cost "
                     "of throughput on cp.meter.",
           "secret": False,                       # required, default False
           "stability": "tunable",                # tunable | structural | dev-only
       },
       # plus the standard Pydantic constraints:
       ge=0, le=1000,
       pattern=r"...",
       # or use Literal[...] for closed enums.
   )
   ```

   The `description=` is **mandatory** — adding a field without one
   fails the new test in `tests/unit/test_settings_metadata.py`. Same
   for `category`, `impact`, and `secret`.

2. **A generator script** at `scripts/render_config_reference.py`
   reads `Settings.model_fields`, groups by `category`, and emits
   `docs/11-configuration-reference.md`. The script is deterministic:
   the same model produces byte-identical output.

3. **A CI staleness gate** runs the generator and fails the pipeline
   if the produced file differs from the checked-in
   `docs/11-configuration-reference.md`. This means a developer
   changing `Settings` either regenerates the doc (one make target)
   or sees CI red. Drift is impossible.

4. **A `.env.example`** is generated by the same script so the dev
   stack has a single source of truth for "what env vars exist."
   Operators can `cp .env.example .env` and edit. Secrets in the
   example are blanked out (`EVEYS_OCPP_BACKEND_TOKEN=`); the
   generator refuses to commit an actual value into the example.

### Category taxonomy (closed enum, validated by the generator)

```text
ws_server          – WebSocket bind address / port.
grpc_server        – gRPC bind address / port.
kafka_producer     – brokers, acks, idempotence, linger, timeout, retry.
kafka_topics       – the four Kafka topic names.
redis              – Redis URL, registry TTL.
postgres           – DB URL, pool sizing.
identity           – pod_id (downward API in k8s).
logging            – log level, log_json.
ocpp_defaults      – heartbeat_interval_seconds, etc.
cross_pod_bus      – bus_request_timeout_seconds.
idempotency        – idempotency_ttl_seconds.
clickhouse_ingest  – host / port / db / group / batch knobs.
backend_integration – base URL, token, per-endpoint timeouts/retries,
                      circuit breaker, fallback policy.
authorize_cache    – enabled, ttl_seconds.
```

Adding a category is a single-line edit in the generator + a row in
this ADR. Categories are **closed** — an unrecognised category fails
the generator. This keeps the doc's table-of-contents stable.

### `stability` field

A field's `stability` answers "what happens to operators who rely on
this exact behaviour":

- **`tunable`** — operator-facing, safe to change at runtime, no
  schema or wire-format consequences. Examples: log level, Kafka
  linger, Redis TTL, Authorize cache TTL.
- **`structural`** — changing it changes how the service binds to
  the world. Examples: bind ports, DB DSN, Kafka brokers, the four
  Kafka topic names. Changes need coordination with whoever else
  reads/writes those topics or DSNs.
- **`dev-only`** — used by tests or local-only stacks; not meant for
  production. Examples: a future debug-mode toggle.

The generator surfaces `stability` as a column in the doc so an
operator skimming for "what can I change without coordinating" gets
the answer immediately.

### `secret` field

Distinct from `stability`. A field is `secret: True` iff its value
is sensitive (token, password, signing key). The generator:

- Emits a blank value in `.env.example` for these fields, with a
  `# secret — fill from your secrets manager` comment.
- Tags them visibly in the reference doc.
- Currently flagged secret: `backend_token` (bearer token) and
  `db_url` (the SQLAlchemy DSN, because production DSNs always carry
  a real password). Phase 5 vault work (E5-7) will move both to
  `pydantic.SecretStr`; the metadata flag is what tells the generator
  to treat them specially in the meantime.

## Consequences

### Positive

- One place to read, one place to write. Operators do not need to
  search the codebase to find what `EVEYS_OCPP_KAFKA_LINGER_MS` does.
- Drift is mechanically impossible: CI fails when the doc and the
  model diverge.
- Adding a new setting becomes a checklist of mandatory metadata.
  Reviewers can mechanically check "does this Field have a
  description, a category, an impact, a secret flag?"
- The `.env.example` stops drifting from `Settings` for the same
  reason.
- Future operator UI / Helm `values.yaml` defaults / CLI `--help`
  output can all consume the same metadata. Today's Markdown is the
  first projection; nothing about this design rules out a JSON
  schema export later.

### Negative

- Every existing `Settings` field needs a one-time backfill (~46
  rows). This MR only writes the spec; the implementation MR
  (E0-12) does the backfill. Estimated 0.5–1 day.
- A second test gate (`tests/unit/test_settings_metadata.py`) +
  one CI staleness check. Cheap (<1 s); negligible CI surface.
- Developers can't sneak in a quick `Field(default=42)` without
  metadata. That's the whole point — but it does add a small
  speed-bump.

### Rejected alternatives

- **Hand-write a doc and trust review to keep it current.** That's
  the status quo. It already drifted: `kafka_topic_cp_meter` has no
  `description=`, `pod_id`'s description omits the k8s downward-API
  note that's relevant to every operator, and the `clickhouse_*`
  fields have inline comments but no descriptions visible to a doc
  generator. Review-driven discipline does not survive contact with
  PR pressure.
- **Use Sphinx autodoc against `Settings`.** Renders the docstrings
  but not the `Field(default=...)` value, and not the constraints
  (`ge=`, `le=`, `pattern=`). The operator wants the range, not
  the type signature.
- **Generate to OpenAPI / JSON Schema and embed via a Sphinx
  extension.** Too much chrome for a flat list of env vars. We can
  always do this later if a JSON-Schema-consuming surface (operator
  UI, k8s ConfigMap validator) lands. The Markdown projection
  doesn't preclude it.
- **Per-section ADRs that include their fields' tables inline.** The
  Kafka knobs would land in ADR-0019, the backend knobs in ADR-0023,
  etc. Operators don't think "which ADR" — they think "what does this
  variable do." A flat reference page wins.

## How operators read this in practice

After this lands, an operator who's seen `EVEYS_OCPP_KAFKA_LINGER_MS`
in a values.yaml does:

```bash
# In the docs site (or `cat docs/11-configuration-reference.md`):
# Ctrl-F kafka_linger_ms
#
# row tells them:
#   - category: kafka_producer
#   - default: 5
#   - range: 0..1000 (ms)
#   - stability: tunable
#   - secret: false
#   - description: producer-wide linger; aiokafka does not support
#     per-call linger override.
#   - impact: lower → tighter cp.meter latency, smaller batches,
#     higher producer overhead. Higher → opposite.
```

No grep. No git log. No reading three ADRs.
