# ADR-0017 — Idempotency cache for inbound OCPP replays

- **Status**: Accepted
- **Date**: 2026-04-30
- **Author**: Eveys engineering (E2-11; AI-assisted draft, human-reviewed and merged)
- **Reviewers**: Project tech lead (post-merge sign-off)

## Context

OCPP chargers retry inbound calls aggressively when the CSMS reply is lost (network blip, pod restart, ack delay). Real fleet deployments see this every day — typical chargers retry 3–5 times within a minute. AGENTS rule 3 calls out two specific actions where double-processing matters:

- **`BootNotification`**: a duplicate emit on `cp.boot` reaches the platform consumers (mobile BFF, fleet dashboards) and looks like the charger booted twice.
- **`StopTransaction`**: a duplicate emit on `tx.stopped` (when that topic ships) — or a duplicate side effect against the session/billing service — would charge a customer twice.

Until E2-11 we had only DB-layer dedup on `StopTransaction` (a synthesized `(cp_id, transaction_id, meter_stop)` natural key). `BootNotification` had no dedup at all, so a flaky charger's first connection produces a flood of `cp.boot` events.

Forces:

- We already run Redis (registry, command bus). Adding a different store doubles operational surface.
- Replay windows are short — typically seconds, almost never minutes.
- Cache outage must not wedge the OCPP handler. A stuck handler propagates as no-response-to-charger and triggers more retries.
- The OCPP frame's `MessageId` (an opaque string generated by the charger; the spec requires only per-call uniqueness, not a particular format) is the natural dedup key. Chargers reuse the same `MessageId` across retries of the same logical request — this is the property we depend on. We do **not** depend on `MessageId` being globally unique, randomly distributed, or stable across power cycles.

## Decision

A small Redis-backed cache keyed by `(cp_id, message_id)` with a short TTL. New module: `src/eveys_ocpp/idempotency.py`. The cache exposes one operation:

```python
async def check_and_record(*, cp_id: str, message_id: str) -> bool: ...
```

…implemented as `SET key "1" NX EX <ttl>` so the test-and-set is atomic in one round-trip.

`BootNotification` and `StopTransaction` consult the cache on entry. Cache hit → return the canonical Accepted response without DB write or Kafka emit. Cache miss → handler proceeds; the key is now recorded.

Default TTL: **300 s (5 min)**. Real OCPP retry storms resolve within seconds; 5 min gives generous margin. Longer TTLs accumulate keys without much benefit — and create a window in which a charger that *does* reuse `MessageId`s (e.g. a vendor that resets its counter on power cycle) could see a legitimate fresh frame mistakenly treated as a replay. The 5-min window is short enough that the same charger booting twice within it is rare in practice, large enough to absorb realistic retry behaviour. Tunable via `Settings.idempotency_ttl_seconds`.

`StopTransaction`'s pre-existing DB-layer dedup stays in place. Two layers on purpose:
- **Redis (E2-11)**: fast, catches the common case (retries within seconds), saves the DB round-trip.
- **Postgres `idempotency_key`**: durable across Redis flushes and TTL expiry. Defense in depth.

The two layers don't conflict — both detect "I've seen this," both return Accepted, neither writes twice.

The OCPP `MessageId` reaches the handler via the `mobilityhouse/ocpp` library's `call_unique_id` kwarg, which is forwarded only when the dispatch method declares it explicitly (`inspect.signature` check inside the library). We add `call_unique_id` to `EveysChargePoint.on_boot_notification` and `.on_stop_transaction` and pass it to the inner handler as `message_id`.

## Alternatives considered

- **Postgres-only dedup with a dedicated table** — durable forever, no TTL. **Rejected:** writing one row per inbound replay-able message at fleet scale (millions/day) would dominate Postgres write traffic. Redis is the right tool for high-volume, short-TTL state.
- **Application-level in-memory `LRUCache`** — fastest, no Redis round-trip. **Rejected:** would not survive pod restarts (chargers retry across minutes; pod restarts happen at any time). Also would not catch cross-pod retries when a charger reconnects to a different pod after a network blip.
- **Use `MessageId` natively as a Postgres unique constraint** — let the DB layer reject the duplicate. **Rejected:** every inbound message would need to be persisted to detect the duplicate, even read-only ones. Same volume problem as above. Redis is simpler.
- **Reuse the `idempotency_key` shape (synthesized natural key)** — already works for `StopTransaction`. **Rejected as primary mechanism:** doesn't extend cleanly to `BootNotification` (no natural-key triple); also pays a DB round-trip per replay where Redis can answer in <1ms.

## Consequences

### Positive

- Replays of `BootNotification` no longer produce duplicate `cp.boot` events. Same for `StopTransaction`.
- Phase 3 platform integration (auth, session, device, billing) gets a clean per-event guarantee on the two AGENTS-named handlers.
- Cache miss costs a single Redis round-trip (~0.5ms locally, <2ms cross-pod). Imperceptible vs the OCPP RTT.
- Adds zero new infrastructure — same Redis the registry and bus already use.

### Negative / costs

- Adds a Redis dependency to the inbound critical path for two handlers. They previously didn't touch Redis. This widens the blast radius of a Redis outage.
- Mitigation: cache outages **fall through** — handlers log a warning and proceed as if the cache miss said "fresh request." Better a rare double-write than a wedged handler. Documented in the handler module-docstrings.
- One extra Redis key per inbound `BootNotification`/`StopTransaction` for the TTL window. At 10k chargers × ~hourly reconnect storm × 5min TTL, that's ~10k keys at any moment. Redis handles this trivially; flagging for awareness.
- `StopTransaction` now has two layers of dedup. The Redis layer catches the hot path; on cache hit the handler returns before any DB work. On cache miss (first sighting) or cache outage (Redis down, fall-through), the DB-layer `idempotency_key` UPDATE still runs — and on a replay that bypasses the cache, that UPDATE runs and matches zero rows (the row already shows `applied=False`). Cost is small but non-zero: connection from the pool, query parsing, brief lock. Acceptable as defense in depth; flagged so future refactors don't assume the DB layer is free.

### Risks

- **Wrong TTL.** 5 min is a guess based on industry retry behaviour. If real chargers retry over longer windows, replays past the TTL would slip through. Mitigation: make TTL configurable via `Settings.idempotency_ttl_seconds`, monitor `idempotency.replay_detected` log volume in staging soak.
- **Race on `(cp_id, message_id)` collision across pods.** Atomic via `SET NX`; first-write wins. The losing pod will see "already seen" on its second message and treat it as a replay — correct behaviour by definition.
- **Forward compat.** If `MessageId` semantics ever change (OCPP 2.0.1 uses a different envelope), the cache key needs a version bump. Easy fix; flagged for the OCPP 2.0.1 track.
- **Cache poisoning by a malicious or buggy charger.** The cache trusts the inbound `MessageId` because there's no auth on it at the OCPP layer. A buggy charger sending a frame with a chosen `MessageId`, or a misbehaving (or malicious) charger sending a stream of frames with predictable IDs, can cause subsequent legitimate frames carrying the same `MessageId` to be silently dropped as "replays" — observable as missing `cp.boot` events or transactions that never recorded their stop. The risk is partial because (a) the cache is keyed by `(cp_id, message_id)`, so an attacker can only poison their own charger's namespace, and (b) Phase 5 lands per-charger Basic-Auth at the WS edge ([E5-6](../02-tasks.md)) and OCA Advanced Security profile mTLS ([ADR-0005](./0005-certification-target.md)), which together constrain who can publish frames as a given `cp_id`. Mitigations beyond Phase 5: monitor `idempotency.replay_detected` rate per charger — a healthy charger sees ≪ 1 replay per BootNotification across the lifetime of a session; a poisoning attack shows up as a high-rate spike on one `cp_id`.

### Reversibility

Reversible. The cache is a thin module behind a single dependency-injected attribute on `EveysChargePoint`. Removing it is a 5-line revert. Switching to a different backend (e.g. an in-process LRU) is also straightforward — change the implementation behind `IdempotencyCache.check_and_record`.
