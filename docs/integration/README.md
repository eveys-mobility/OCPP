# Backend ↔ `eveys/ocpp` integration spec

> **Audience**: backend developers wiring the Eveys backend to the OCPP gateway.

This directory is the contract between the Eveys backend and `eveys/ocpp` (the OCPP gateway). It defines the two REST surfaces and the webhook deliveries that connect them.

## Read order for backend devs

1. **[01-backend-rest-contract.md](./01-backend-rest-contract.md)** — endpoints **the backend implements** for the gateway to call. These are the synchronous OCPP-hot-path calls (Authorize, session open/close, charger registration). **Start here** — the gateway can't go to production until these exist.
2. **[02-gateway-rest-api.md](./02-gateway-rest-api.md)** — endpoints **the gateway exposes** for the backend to call. Read state (presence, transactions, MeterValues time-series) and issue OCPP commands (RemoteStart, Reset, Unlock, …). The backend is the client; consume what you need.
3. **[03-webhooks.md](./03-webhooks.md)** — gateway → backend webhooks. Async fire-and-forget pushes for events the backend wants to learn about without polling.

The corresponding decisions are captured in [ADR-0023](../adr/0023-backend-rest-integration.md).

## Conventions (apply to all three docs unless overridden)

### Base URLs

| Surface | Convention |
|---|---|
| Backend (where the gateway calls) | `<eveys_backend_base_url>/api/eveys/...` |
| Gateway (where the backend calls) | `<eveys_ocpp_base_url>/api/v1/...` |
| Webhook delivery | `<eveys_backend_base_url>/api/eveys/webhooks/...` (operator-configurable per event) |

### Response envelopes (asymmetric)

The two surfaces use **different** response shapes — picked deliberately:

**Backend endpoints** (`/api/eveys/...`): every response — success and error — uses the envelope:

```text
{
  "success": true,
  "data": { ... },
  "message": "human-readable summary"
}
```

```json
{
  "success": false,
  "data": null,
  "message": "human-readable error description",
  "error_code": "STABLE_CODE_FOR_PROGRAMMATIC_USE"
}
```

**Gateway endpoints** (`/api/v1/...`): success returns **raw JSON** without an envelope, in the gRPC-style "the response *is* the data" idiom.

Success (top-level is the resource):

```json
{
  "cp_id": "CP_ACME_42",
  "online": true
}
```

Error (consistent shape):

```json
{
  "error": "human-readable",
  "error_code": "STABLE_CODE",
  "request_id": "<uuid>"
}
```

Backend developers consuming both surfaces remember: **outbound calls (gateway → backend) return the envelope; inbound calls (backend → gateway) return raw JSON**. The asymmetry is documented at the top of each spec and in every example.

JSON field naming — snake_case or camelCase — is flexible per surface. Pick one and stick with it; the gateway translates at the HTTP boundary regardless of choice.

### HTTP status codes

The envelope's `success: true | false` plus `error_code` is the source of truth for outcome. HTTP status codes still apply at the transport layer:

| Code | Meaning |
|---|---|
| `200 OK` | Logical success or business-rule outcome (`{"success":false}` for "id_tag invalid" still returns 200). |
| `400 Bad Request` | Malformed JSON, schema violation, missing required field. |
| `401 Unauthorized` | Bearer token missing / invalid. |
| `403 Forbidden` | Token valid but lacks scope for this endpoint. |
| `404 Not Found` | Path doesn't exist OR `cp_id` unknown to the system. |
| `409 Conflict` | Idempotency-key conflict (replay with mismatched body). |
| `429 Too Many Requests` | Rate-limit exceeded. Honor `Retry-After`. |
| `5xx` | Server failure on the responder side. The caller should treat as retryable per the spec for that endpoint. |

A `200` with `success: false` and a stable `error_code` is the **business-error path** — the request was valid, the system understood it, and the outcome is a known "no". Examples: `id_tag` blocked, transaction already closed, charger offline.

A `4xx` / `5xx` is a **transport-level error** — the request couldn't be processed. Caller retries per the per-endpoint policy.

### Authentication

Both surfaces use **Bearer tokens**:

```
Authorization: Bearer <token>
```

- **Gateway → Backend**: token issued by the backend (service account). Stored in the gateway as `EVEYS_OCPP_BACKEND_TOKEN` env var (Phase 5 will move it to a vault per E5-7).
- **Backend → Gateway**: token issued by the gateway (one per consumer). Validated against a configured allowlist. Stored in the backend's secret store.

Phase 5 (E5-5 mTLS) will upgrade both directions to mutual TLS; bearer tokens remain as a fallback layer of defence.

### Correlation IDs

Every request — both directions — carries:

```
X-Request-ID: <uuid v4>
```

Generated by the caller. The responder echoes it in the `X-Request-ID` response header so log lines on both sides correlate. Gateway logs bind it to `trace_id` for distributed tracing.

The header is the canonical correlation channel. Endpoints may also include `request_id` and / or `command_id` fields *inside* the response body when useful:

- **`request_id`** — same value as the inbound `X-Request-ID` header. Convenient for clients that prefer to read it from the body.
- **`command_id`** — a stable, responder-assigned identifier for any command-shaped resource the responder persists. The gateway uses it on its command endpoints (`POST /api/v1/charge-points/{cp_id}/commands/...`) to give the backend a handle for ops correlation.

Whether to include either inside the body is a per-endpoint choice; see the per-endpoint specs.

### Idempotency

Hot-path endpoints that mutate state — `POST /api/eveys/sessions/open`, `/sessions/close`, every `/api/v1/charge-points/{cp_id}/commands/*` — accept an idempotency key:

```
Idempotency-Key: <opaque caller-supplied string, ≤ 64 chars>
```

Replay with the same key + identical body returns the original response (cached for 24h). Replay with the same key + **different** body returns `409 Conflict`. Endpoints that are naturally idempotent (e.g. `register` upsert, all `GET`) ignore the header.

### Timestamps

ISO-8601 UTC with millisecond precision:

```
2026-05-05T14:32:11.847+00:00
```

We do not use Unix-epoch numbers anywhere on the wire. Per-charger reported timestamps (charger's local clock, untrusted per AGENTS rule 7) are tagged as `chargerReportedAt` to distinguish from server-receive `receivedAt` / `occurredAt` timestamps.

### Webhook signatures

Gateway-to-backend webhook deliveries carry:

```
X-Eveys-Signature: sha256=<hex of HMAC-SHA-256 over raw request body>
X-Eveys-Event-Id: <uuid v4>
X-Eveys-Event-Type: cp.status_changed
X-Eveys-Delivered-At: 2026-05-05T14:32:11.847+00:00
```

The shared secret is per-environment, configured in the gateway's `EVEYS_OCPP_WEBHOOK_SECRET` env var. The backend MUST verify the signature and MUST be idempotent on `X-Eveys-Event-Id`. Full details in [03-webhooks.md](./03-webhooks.md).

### Versioning

Both surfaces are at `v1`. Breaking changes require a `v2` path; additive changes (new fields, new endpoints) are non-breaking and may ship without a version bump. The same gate that guards proto compatibility (ADR-0018, `buf breaking`) doesn't apply to JSON, but the same *intent* does — adding fields is fine, removing or renaming is not.

## Sequencing

The recommended implementation order (dictated by what unblocks what):

1. **Backend implements [01](./01-backend-rest-contract.md) `/authorize`, `/sessions/open`, `/sessions/close`** — the OCPP hot path. Nothing else can be wired until these exist. Gateway-side mocks let the backend dev work without a running gateway.
2. **Gateway-side wiring** of those calls into the corresponding handlers (Authorize, StartTransaction, StopTransaction). Done in `eveys_ocpp.platform.*` modules with timeout / retry / circuit-breaker.
3. **Gateway implements [02](./02-gateway-rest-api.md) read endpoints** for backend dashboards / billing. Largely thin wrappers over Postgres + ClickHouse.
4. **Webhooks** ([03](./03-webhooks.md)) — the gateway publishes; backend chooses which to subscribe to.
5. **Gateway implements [02](./02-gateway-rest-api.md) command endpoints** (RemoteStart, Reset, etc.) — these are HTTP wrappers around the 19 OCPP gRPC RPCs. Mostly translation work; can ship in parallel with steps 3-4.

Each step is a separate MR; the E3-1..E3-9 task IDs in `docs/02-tasks.md` map onto these.
