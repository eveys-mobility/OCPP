# Envoy edge config (E5-1, ADR-0007)

Envoy is the load balancer that sits between chargers and the
gateway pods in production. Two configs live here:

- `envoy.local.yaml` — the **compose-mode** dev variant.
- `envoy.yaml` — the **k8s production** variant.

Keep them in sync. Diverging edge behaviour between dev and prod
is exactly what Tier-3 compose-smoke (ADR-0024) was added to catch.

## Sticky-hash contract

Both configs hash on `:path` to pick the upstream pod. The
gateway's WS server interprets the URL path as the `cp_id`
(`src/eveys_ocpp/transport/ws_server.py`), so hashing on path
gives consistent-hash on `cp_id`. A charger reconnecting after a
brief drop lands on the same pod, preserving registry ownership
(ADR-0016) and avoiding cross-pod gRPC bus round-trips.

**If a future protocol shape moves `cp_id` out of the path** (a
query string, a custom header, etc.), this hash key becomes
inconsistent. ADR-0007 documents the coupling. Coordinate any
URL-shape change with an Envoy config change.

## What the filter chain does

| Filter | Purpose | Status |
|---|---|---|
| `envoy.filters.http.local_ratelimit` | WS-upgrade rate cap (E5-2). `local_rate_limit_per_downstream_connection: true` gives each TCP connection its own 60-token bucket refilling at 30/min — covers the per-IP-attempt-rate goal at the protocol level (WS upgrade is the first request on every charger connection). `X-RateLimit-*` headers exposed. With 2+ Envoy replicas the effective cap multiplies; aggregated per-IP via RLS deferred until measured need. | Active |
| `envoy.filters.http.router` | Forward to upstream | Active |

`upgrade_configs: websocket` is the load-bearing piece for the
WebSocket-upgrade path; without it, Envoy closes the connection
right after the HTTP/1.1 handshake.

`stream_idle_timeout: 0s` and `request_timeout: 0s` are required
on listeners + routes — Envoy's defaults would reap idle WebSocket
streams.

## Health checks

Envoy probes `/api/v1/ready` (the readiness endpoint added in PR
#43) on each upstream pod. A 503 here removes the pod from
rotation, which is exactly the graceful-drain signal — the
gateway flips `/ready` to 503 on SIGTERM, holds for the configured
propagation window, then exits. Envoy stops sending it new
connections during that window.

## TLS / certs

- **Compose dev**: self-signed certs generated by
  `scripts/gen-dev-certs.sh`. Output goes to
  `deploy/envoy/certs/` which is `.gitignore`-d.
- **Production**: certs are mounted from cert-manager,
  external-secrets-operator, or whatever the platform uses. The
  Helm chart at `deploy/helm/eveys-ocpp/` configures the mount;
  the cert lifecycle itself is operator territory.

## Bringing up the dev stack with Envoy

```bash
scripts/gen-dev-certs.sh    # one-shot, idempotent
make compose-up             # brings up everything including envoy
```

A charger sim then connects via:

- `ws://localhost:19000/<cp_id>` — direct to the gateway, bypasses Envoy. Existing tests use this path.
- `wss://localhost:19443/<cp_id>` — through Envoy's TLS listener. Use `--insecure` (or equivalent) on the client because the cert is self-signed.

Both paths land at the same gateway. The TLS path exercises the
production-shaped routing.

## Validating config changes

```bash
docker run --rm -v "$(pwd)/deploy/envoy:/etc/envoy" envoyproxy/envoy:v1.31-latest \
    envoy --mode validate -c /etc/envoy/envoy.local.yaml
```

This runs Envoy's own config parser without binding listeners,
so it's safe in CI. The `infra-validate` GitHub Actions job runs
this on every PR.
